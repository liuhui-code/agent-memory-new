# Relationship retention: two losses, not yet one demonstrated contract

Read-only design review of the frozen evidence. No new query, source variant,
parameter, runtime edit or test execution accompanies this report.

## A. Strong lexical endpoints lose promotion provenance, then compact narrows

Evidence: `../cross-preview-current/README.md`, `graph-trace-*.json`, and the
independent/prop-equivalence score traces in that directory (score addendum
commit `3b34596`). The original Development group remains 1/3.

Both parent and child exist in raw. `promote_neighbor` only records the graph
promotion when its proposed score exceeds the existing match. Original forward
passes_property proposal 50.17 is below child 67.5; reverse 54.52296 is below
parent 56. The render proposals also lose. Compact `focus_callable_anchors`
subsequently removes the child while treating graph-neighbor provenance as a
reason not to narrow.

This couples two different questions: whether a relation improves rank, and
whether a verified relation is available to a later retention decision. Keeping
relation provenance independent of rank is a plausible representation invariant;
it does NOT itself establish that this request needs both endpoints, nor that
compact must preserve them. The latter remains a selection policy decision.

Crucial gap: the independent four-query fixture and fixed prop rename are green.
Their forward property score 48.17035 exceeds child 44.25, whereas reverse
40.535 is below parent 64.5. They do not cover both-direction suppression. This
is untested independent public branch coverage, not a falsified hypothesis and
not permission to manufacture lexical scores until the query fails.

## B. A true weak relation is retained in graph output, then raw drops it

Evidence: `FIRST-LOSS.md`, `first-loss-raw-trace.json`, `branch-raw-trace.json`.
The one attributed official-document Development task is red. Verified
TodoListComponent file ID 6 passes_property/renders_component to ThingComponent
symbol ID 10, range 4–45. Resolution, MAX_GRAPH_NEIGHBORS=2 and focus retain it.
`diverse_code_matches` first drops it: index 12, score 19.55 < seed 70.5 / 2,
selected_count 4, limit 5, no reserved lane. It never reaches compact.

Unlike A, relation provenance is present. The existing weak-neighbor rule is
working as written. Ranking strength is being used as evidence-selection policy,
but no inspected contract binds this particular candidate to the requested child
role and exempts it. A real static edge alone is insufficient: a task can request
only a parent, or another relation can be incidental. The available final slot
proves neither global budget fit nor entitlement to displace a direct result.
This is a demonstrated public task failure, not yet a proven implementation
violation of a request-conditioned retention contract.

## Architecture threshold: NOT met

The repository requires two independent defect classes demonstrating the same
missing contract before architecture changes. A and B suggest a shared design
question (rank versus request-conditioned relationship evidence), but are not
interchangeable proofs. A lacks independent public coverage of its actual branch;
B lacks a demonstrated request-to-relation admission contract. Both also concern
component relationships, so distinct source lineage and distinct failing layers
alone must not be counted as two independent defect classes. These observations
justify design review, not a new universal relationship bundle or promotion rule.

## Smallest falsifiable contract to review next (not implemented)

Separate two candidate invariants rather than grant a blanket graph exemption:

1. **Evidence identity invariant:** for an already resolved static relation,
   recording its typed endpoints/source provenance is independent of whether its
   score beats an existing lexical match. It grants no rank, owner, causality,
   completeness or retention authority. A deterministic internal boundary test
   could cover proposed score below/equal/above existing score with identical
   relation identity. That is useful unit evidence, NOT the missing public red.
2. **Conditional retention obligation:** only when a separately specified,
   auditable request binding requires both source roles may a selector preserve
   their evidence together instead of invoking unrelated weak-neighbor or
   callable narrowing policy. The current data do not establish that binding.
   Define it first, including explicit refusal/ambiguity outcomes, before testing
   or implementing a consumer. No new parser or role certificate is approved here.

Required review evidence before acceptance:

- A fresh independently sourced, pre-frozen public case must actually reach A's
  double-suppression branch and fail at compact, without score/query tuning.
  If it does not, stop and report missing coverage. Keep official B unchanged.
- Positive pairs must have resolved project-local endpoint kind/ID/path/range,
  source digest/freshness, actual property/render source support and the required
  excerpts. Do not conflate file import, method call and component render roles.
- Negative controls must retain single-parent/child-only requests, unrelated
  imports/graph neighbors, multiple real children/callers, same-name identities,
  literal/declaration requests and actual log requests. "Both" is not automatic
  proof of which two candidates; generic or ambiguous role binding stays unknown.
- Test rank evidence storage separately from retrieval privilege. Adding metadata
  must not silently activate broad graph-neighbor preservation in existing consumers.
- Under insufficient total tokens, source caps, per-anchor limits or stale/missing
  bytes, preserve existing hard bounds and expose incompleteness; do not drop other
  required owners, logs, uncertainty or typed identity to declare success. No new
  global-uniqueness or execution/causal claim follows from a bounded candidate set.

Concrete next review gate: approve or reject the evidence-identity invariant and
an explicit request-binding specification separately. An internal boundary test
can then audit the former without changing serving behavior. No new public source
search, query series or architecture implementation is authorized by this report.
