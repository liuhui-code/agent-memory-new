## Existing contract is not being dropped

query_typed_contract explicitly covers a single named parameter, return type,
declaration or literal relation, plus an explicitly requested invocation on that
parameter. Its contract is conservative and specifically does not infer data flow.
The original generic binds...contract query matches none of those declared forms;
classify_contract correctly returns None under the existing contract. Plain
callback_binding mechanism evidence identifies name-shaped calls, not a proof of
observer registration -> callback execution -> same typed receiver forwarding.
Both the enclosing method and nested callback may expose those lexical mechanisms.
No already-defined binding proof was found being lost between producer and consumer.

A genuine extension would need independently specified semantics for requested
binding versus declaration/parameter/forwarding, then source-bound registration,
callback containment, exact receiver/parameter identity and method invocation;
shadowing/rebinding, nested callbacks, aliases, interface-only declarations, unused
parameters, genuine retry and multiple-forwarder cases must remain supported or
unknown. The present single defect family is not a justification for a new broad
architectural authority, and there is no safe narrow implementation patch yet.
