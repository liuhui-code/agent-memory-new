# 元反思的跨任务、跨版本递归演进方案

日期：2026-10-30。核对基线：`4d5e068e68a107437aee2df7edd39acb595d311f`。
本文是研究支持的演进草案。2026-11-01 已实施 [R1 只读结果关联](system-meta-reflection-outcomes.zh-CN.md)
和 [R2 持久轮次](system-meta-reflection-rounds.zh-CN.md)，随后加入
[R3 宿主窗口交接](system-meta-reflection-handoffs.zh-CN.md)；正常任务自动采样、自动候选/部署
及真实长期效能仍不在已完成范围。
随后按用户选择完成 [R4 开发准备](system-meta-reflection-campaign-readiness.zh-CN.md)，真实活动保持未启动。
批准字段留空；本轮用户授权调研和完善方案，不据此补造规范批准或真实活动输入。

## 1. 结论与成熟度

可采用的完整路径是：连续真实任务形成反馈，当前 Agent 生成系统改进候选，独立验证后
按授权应用，再由后续任务检验改动及其生成方法。递归对象包括规则、Query、Learn、
Reflect、元反思、评测器、数据结构和交付；宿主模型权重不在本方案的修改范围内。

成熟的基础来自持续改进、自治计算、运维复盘和受控实验。AI 提示/代码演进已有论文及
特定生产应用；这些材料支持有范围的试验方法，不能保证任意系统持续、单调变好。
本方案采用两个节奏：任务收尾形成快反馈，冻结的观察窗口结束后进行跨版本复核。
递归通过下一轮版本谱系表达，同一任务内仍只执行一次自动评审。

### 理论和实际实践

以下“采用方式”是本项目的设计推断，来源中的结果不迁移为本项目收益。访问日期均为本日。

| 来源与成熟度 | 来源支持的机制 | 本项目采用方式与限制 |
|---|---|---|
| [Argyris 双环学习](https://hbr.org/1977/09/double-loop-learning-in-organizations)，1977，经典理论 | 学习也检视行动背后的假设 | 规则和反思方法也可成为候选；既有授权和证据政策继续适用 |
| [Deming Institute：PDSA](https://deming.org/explore/pdsa/)，成熟持续改进方法 | 先提出理论和成功指标，实施后研究实际结果，再调整方法或理论 | 每轮先写可证伪预期；复核包括结果不符的解释，不以“完成检查”代替学习 |
| [Kephart / Chess：自治计算](https://www.csd.uwo.ca/~hlutfiyy/cs843/papers/Autonomic_vision.pdf)，2003；[IBM MAPE-K 报告](https://dominoweb.draco.res.ibm.com/reports/h-0219.pdf)，2004 | 监测、分析、计划、执行共享知识，按外部目标管理受控系统 | Runtime 提供观测和显式执行；Agent 分析与设计；沿用 SQLite，不由 Runtime 产生诊断结论 |
| [Google SRE：复盘及行动项](https://sre.google/workbook/postmortem-culture/)，生产实践 | 行动项有负责人、可核对终态和跟踪；定期复核复盘过程与重复故障 | 把报告关联到提案、应用和复发结果；跨窗口核对触发与评审规则本身 |
| [Google SRE：Canary](https://sre.google/workbook/canarying-releases/)，生产实践 | 有限范围、有限时间比较候选与控制；选择有代表性且可归因的指标 | 本地项目采用限定安装目标/任务队列观察；没有控制组时只报关联。合成安装测试不称真实 canary |
| [Microsoft ExP：实验前](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-pre-experiment-stage/)与[实验中](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/patterns-of-trustworthy-experimentation-during-experiment-stage/)，规模化生产实践 | 预先声明假设，区分总体目标、诊断、护栏及数据质量指标 | 一轮一个主要假设；质量、成本和完整性分别报告；不边看结果边改停止或通过条件 |
| [Reflexion](https://arxiv.org/abs/2303.11366)，2023，研究 | 通过反馈及语言反思改变后续行为，不更新模型权重 | 当前模型可生成提案；语言反馈和模型自评保留为建议，不能认证有效性 |
| [GEPA](https://arxiv.org/abs/2507.19457)，2025/2026，提示优化研究；[ACE](https://arxiv.org/abs/2510.04618)，2025 起，上下文演进研究 | 分别探索反思驱动的提示候选、结构化上下文增量更新 | 保留候选和来源，优先小步差异；不导入私有推理轨迹或整份上下文重写，也不引入框架依赖 |
| [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954)，2025/2026，代码自改研究 | 修改 Agent 代码，保留候选档案，并用编码任务经验验证 | 允许改进改进机制；本项目先串行维护一个活跃候选，保留稳定版本，不复制开放式并行搜索 |
| [AlphaEvolve 白皮书](https://arxiv.org/abs/2506.13131)与[2026-05-07 实践报告](https://deepmind.google/blog/alphaevolve-impact/)，研究及作者报告的生产应用 | LLM 生成代码，执行评估筛选；团队报告已用于基础设施、缓存策略及存储压实启发式优化 | 优先选择可执行验证的算法/结构改动；厂商案例不是本项目复现，也不证明自然语言质量可完全自动判定 |
| [Intrinsic Self-Correction](https://arxiv.org/abs/2310.01798)，2023/2024，特定推理任务研究 | 无外部反馈的自纠正在其研究设置中可能退化 | 同模型可以分析和生成，客观检查与真实结果不能由自评替代；不把该论文泛化为所有当前模型都不能自纠正 |
| [Reflective Prompt Optimization](https://arxiv.org/abs/2610.12601)，2026-10-08，新预印本 | 在特定研究 Agent 中检查主题隔离、多随机种子和验证器影响 | 作为过拟合与判定偏差的补充线索；不将单篇新预印本提升为成熟行业共识 |

采用 PDSA 强调预期与实际结果的比较，采用 MAPE-K 划分职责，采用 SRE/ExP 建立行动项、
观察和对照，再借鉴 AI 工作提出候选。这是一项工程组合设计，没有证明其控制稳定性或收敛性。

来源限制：HBR 网页为预览，双环学习仅作简短概念引用；2004 IBM 报告全文抓取超时，
控制环结构以已读取的 2003 原始论文交叉核对。AlphaEvolve 的实际应用属于团队自报，
本项目未复现其生产收益。其余论文的研究结论只保留对应任务与评估范围。

## 3. 职责、递归边界与触发

```mermaid
flowchart LR
    A[连续真实任务] --> B[任务收尾观察]
    B --> C[Agent 评审与候选]
    C --> D[独立检查与显式应用]
    D --> E[冻结窗口内后续结果]
    E --> F[跨版本复核]
    F -->|新证据与预算齐备| C
    F -->|不足或退化| G[保留基线或回退并停止]
```

任务级反馈识别具体问题；系统改进执行现有候选/应用流程；跨版本复核检查改动效果以及
触发、归因、评审和验证方法。三者是本项目职责划分，不声称业界存在统一的“三环”定义。

- 当前 v1 的 `activity=system_review/system_evolution` 自动跳过规则保留。明确手动请求
  可以评审系统改进工作，但同一来源、任务和轮次必须沿用关联，不制造新独立样本。
- 可在预声明窗口到达终点、有新的可核对结果、且没有未决操作时，由宿主 Agent
  收尾步骤发起一次轮次复核。最初采用明确的批次维护任务；无需守护进程或第五个 Skill。
  R3 已提供这一步的有界交接：v2 结果计划预绑定许可，一次名额先于模型生成，R2 评估和
  完成事件原子保存。已知窗口的 Skill 收尾路径可使用它，不保证宿主必定加载或调用。
- 轮次推进要核对实际终态。日期/间隔到达不证明写者、检查子进程或模型已经终止，不能
  释放未知操作、删除协调锁或重开失败/中断任务的自动评审名额。
- 首阶段沿用每任务一个自动评审、一个提案、4,000 字符报告、无自动重试。对同一改进
  作用域串行观察一个候选；下一轮必须等待本轮决策和必要恢复完成。
- 轮次总数、模型/工具预算、观察终点和停止规则在运行前固定。最初可将最大轮次数设为 3，
  这是建议的工程上限，不是已测最优值；预算未指定时不启用自动跨轮执行。
- 没有新证据时允许读取旧结果或说明缺口，不启动新一轮“再想一次”。同一假设可因新证据
  重新提出，必须保留此前失败、撤回和成本，不能重置谱系或重新使用已消费的 holdout。
  明确新需求也可启动授权开发；它与缺陷证据分账。可重复的 development 检查结果不因
  推进轮次而变成独立效能样本。

## 4. 一轮改进的完整流程

1. 绑定真实项目/Memory Home、任务来源、当前稳定版本、允许改动和已经存在的授权。
   写清可观察问题，区分 defect、requirement、structural，不先把模型推断写成缺陷事实。
2. 冻结主要假设、预期改善、兼容约束、对照方式、样本来源、正常任务审计规则、预算和停止条件。
   后续缺项不补写为“原先已声明”；变更协议需要新版本与新窗口。
3. 分开用于开发的反馈和用于确认效果的未来材料，定位 failing layer。检索改动仍要在独立
   development fixture 和实际 query_handoff 复现；结构抽象仍要两类独立缺陷依据。
4. 当前 Agent 准备一个必要范围内的规则/代码/结构候选，保留完整基线及差异。复用现有
   candidate、v3 check、accept 和 apply，不仅保存一段反思文字。
5. 执行事先声明的功能、反例、兼容、成本和回退检查。规则/查询/学习/反思、评测器和数据
   模型改动分别补齐原政策项；模型对源码使用和语义的审查不获得自动身份/Oracle 认证。
6. 在明确授权的目标应用，核对实际安装字节、数据版本及后续检查。未指定真实目标时停留
   在开发验收；不能将一个临时安装副本记为业务项目已升级。
7. 在冻结窗口内继续自然任务，记录全部到达项、排除项、未验证结果与完整成本。保持当前
   候选、对照和评价规则稳定，不在观察途中悄悄修改产品规则、评分或样本选择。
8. 到达终点后分别报告机制验收、自然观察和受控对照。必要时保留基线、回退或声明未知；
   后续轮次只消费允许使用的结果提出新假设，原始记录、失败及历史决策保持可追溯。

## 5. 改进对象与对应验证

| 对象 | 可形成的实际改动 | 本轮必须说明的效果依据 |
|---|---|---|
| 系统规则/Skill | 激活、展开、学习范围或停止策略差异 | 不该调用/应当调用的受控案例、真实调用观察、总成本和协议保留 |
| Query | 召回、排序、过滤、压缩或来源检查补丁 | 公共输出独立复现、预声明目标改善、原能力与预算回归；允许有意算法变更，不冻结全部旧排序 |
| Learn | 选择、提取、刷新、去重或失效传播补丁 | 已知来源的预期提取/删除/代次及下游查询，不用索引数量增加代替质量 |
| Reflect/元反思 | 信号、归因、提案和补证规则差异 | 已知预期的误报/漏检审计、实际可复现提案、复发和额外成本；报告长度与自评分不作效果指标 |
| 数据结构 | 版本化实体/字段/关系/索引及迁移 | 语义映射、读写矩阵、中断重试、数据保留与升级后写入；每种新模型有自己的实现，不能套用治理 v1/v2 的通过结果 |
| 评测器 | 判定规则或观测实现补丁 | 已知预期受控案例的误判证据；与产品候选分开修订，不用新标准为同轮候选追认成功 |
| 交付/维护 | 安装升级、定位、恢复与版本配套补丁 | 实际安装和故障恢复、无关文件保留、重复执行与迁移边界 |

普通记忆内容修订继续使用原有路径。把系统规则存成一条业务事实不能赋予它执行权限，
元反思意见也不直接成为 verified/confirmed 检索反馈。

## 6. 最小逻辑记录与数据演进

以下是完整目标的逻辑契约，不是 reflect-system 的可提交字段，也不预设四张表。
R2 用一张追加事件表保存当前支持的计划/应用绑定与评估/决策快照；模型、Runner 等不可得
身份不得补造，完整版本/观察合同的其他字段仍按后续切片逐步实现。

| 记录组 | 最小字段语义 |
|---|---|
| 研究/活动 | 实际 project/archive、任务类型与来源关联、连续性责任、允许改动、预算、固定总轮数、主要假设和声明范围 |
| 轮次计划 | round_id、parent_round_id、父稳定版本、目标组件/问题簇、review/proposal 引用、输入截止点、协议/指标/评审器版本、窗口和预算 |
| 观察窗口 | window_id、到达序号范围及纳入/排除规则、分组单位、审计选择规则、对照版本、任务前 source/Memory 绑定、已知遥测缺口 |
| 轮次结果/决策 | 实际检查/应用/回退操作键、样本与缺失计数、分组质量/成本结果、复发记录、结果范围、unknown 原因和 keep/adopt/rollback/inconclusive/stop 决策 |

版本身份分别绑定 Runtime commit/必要的工作区摘要、Skill bundle、查询协议、数据库 schema、
源码/index generation、当前模型可用身份、Runner/执行环境及评审/测量规则。缺失模型精确
版本标为未知；同一个产品名不保证模型实现相同。发生实质变化时分新观察 epoch，保留混杂标记。

同轮修订保留旧计划与结果，重试幂等。后续长期结果可以追加新 assessment，不能覆盖曾经的
负面结果，也不能把已 closed 的提案重写为“已证明长期有效”。已有提案状态保持原语义。

R1 把计划/结果作为授权开发目录中的有界制品，绑定既有提案和操作引用；文件不成为平行产品真源。
R2 已提供最小 SQLite 追加记录、单一显式 writer、备份迁移、兼容读取和受控验证；历史读取
不依赖原文件，记录次数预算不冒充实际模型调用或 Token 限制。不新增数据库或通过查询初始化。
R3 增加独立可选交接组件及 claim/finish 事件，预绑定许可/次数/输出上限；只控制窗口评估
名额和保存，不自动产生下一候选或部署。实际 Token/工具成本和精确模型身份仍不得补造。
v1 严格 payload 不塞入额外字段；模型 SQL 不直接执行。

所有机器记录保留有界摘要、opaque ID、版本、计数及证据引用。原始任务、查询、日志、源码、
完整命令和私有推理不进入治理/效果记录。Git 候选与迁移源码仍保存在授权源码目录，按现有
制品方式管理；需要复核的原始任务仍由 SQLite 外部的已指定位置保管，摘要不能替代原始输入。

## 7. 反馈质量、采样和漏检

| 反馈来源 | 可以支持的判断 | 不能直接支持的判断 |
|---|---|---|
| 模型意见及自评分 | 生成假设、检查方向和语义审查 | 缺陷成立、因果收益、独立 Oracle、外部晋级 |
| 实际工具退出/新产物及源码核对 | 指定命令和约束在该输入上的观察 | 检查有充分覆盖、用户任务正确、长期提升 |
| 真实测试/build/复现及明确用户确认 | 其声明范围内的任务或机制结果 | 自动变成盲审、无混杂因果证据或所有任务泛化 |
| 连续自然任务窗口 | 采用、错误、机会率、复发和结果关联 | 单凭升级前后差异归因于本轮改动 |
| 同 revision 的受控 paired/随机对照 | 其冻结合同与支持样本范围内的差异 | 自动代表自然使用、所有项目或无限期效能 |

当前仅具体异常触发、成功抽样为 0 的默认值保留。为了检查漏检，下一阶段应预先选定正常
任务审计规则，例如在到达时按固定序号选择；选择在结果揭示前确定，不只挑成功或适合 Memory 的任务。
实际无法取得全量到达边界时报告 self-attested；内部连续序号不能认证外部没有漏报。

首阶段可由明确的批次维护任务审计一组真实已登记结果。若以后增加自动正常任务抽样，需要
新的有类型触发/采样协议和去重预算，不能伪造 memory_error/repeated_gap 或把历史活动许可
冒充当前 manual_request。异常和正常审计命中同一任务时共享一次任务评审。

“未发现问题”不等于“已确认没有问题”。提案正确率须报告被审计提案总数、支持/反证/未知
分母；只对已裁定子集计算时明确写出子集。漏检率只有在独立核对得到问题全集/适当采样权重时
才能估计；没有这个分母就标为 unavailable。模型多次评审、同源重试不增加独立证据数量。

## 8. 长期效能与归因合同

### 分账的指标

| 层次 | 观察项 | 解释 |
|---|---|---|
| 用户结果 | 客观验证通过/失败/未知、返工、已确认纠正及任务完成耗时 | 主目标在运行前选定，实际任务难度/类型分层；不把回答长度或锚点分当诊断正确率 |
| 系统机制 | 查询错误、契约违例、旧问题复发、迁移/回退失败、原能力回归 | 直接核对对应改动；没有同类问题机会时不宣称复发率为零 |
| 改进过程 | 报告到可复现提案/应用的覆盖，未知项、复发与撤回 | 作为诊断，不追求报告数、提案数或关闭率最大化 |
| 成本护栏 | 端到端 Token/耗时、额外评审/检查/迁移、人工返工、数据/文件规模 | 同时报总量和可单独测量的增量；未测量填 unknown/null，不能把整回合 usage 当元反思增量 |
| 数据质量 | 到达/排除/完成/缺失计数、版本完整性、分组偏差、遥测缺失 | 先检查是否可解释，再看结果；缺数据不填零，失败和未知项不能从报告分母消失 |

不默认合成单一“自我提升分”。先满足数据质量、协议/数据兼容和成本护栏，再评价预先声明
的主要目标；质量/成本权衡需预声明，不能以一个高分抵消不可接受的退化。

### 设计和来源隔离

- feasibility 活动只估计采用、机会率、遥测完整性和可实施性；样本数在任务前固定。
  真正效能活动需新的协议和来源，根据独立先验/可检测效果决定样本理由。少量任务不是统计功效证明。
- 先用自然队列观察，再选择预声明且符合条件的 paired 来源。不得看到结果后选择最有利
  任务补做对照，也不能把当前对话和历史修复补登记成前瞻任务。
- paired 需相同实际任务、源码 revision/tree、任务前 Memory、模型/Runner、预算及停止规则。
  除预声明的单一候选差异外保持一致；旧 v3 的 Memory-on/off 问题与两个 Memory 版本的
  比较不是同一处理合同，后者需要独立版本化设计。
- Query、Learn 和 Reflect 的副作用不同。写入型比较必须从相同初始快照创建相互隔离的
  可写副本，不共享学习/反思输出污染对照，也不在真实归档试写；当前 query paired 合同
  不自动获得这些新能力。
- 同一来源/任务家族、模型种子和重试之间的依赖要报告；任务集/环境/模型/Memory 的变化
  需分层或开启新窗口。只做时间前后比较时保留混杂，不声称改动导致了收益。
- 开发可重复，独立确认材料须按现有政策分类、隔离和一次性消费。已消费 sealed holdout
  不编辑、不重跑、不用于后续调参；本方案没有“可复用 holdout”的例外。
- 观察中可按预先定义的严重退化条件中止或回退，以保护正常使用；提前中止不计为效能成功。
  正向结论不能因中途分数好就提前停止；多候选/多轮比较也要报告全部尝试及选择过程。
- 保留旧能力 development 回归与新的未来来源，分别看迁移/遗忘和当期任务结果。没有新来源
  时停止扩展，不以反复通过旧测试替代长期证据。

## 9. 评审机制也能改进，但不能追认自身

评审/采样/验证器变更作为 `reflect`、`rules` 或 `evaluator` 的独立候选，先写已知预期
的受控案例与反例，核对错误归因、位置/表述偏差和弃权行为。评测器变更必须已有实际误判证据。

当前轮候选继续按冻结的旧规则评价；确有旧规则缺陷时，本轮判定可以失效或暂停，不能
降低门槛后追认通过。新规则在新的版本/窗口生效，必要时对开发材料运行旧/新规则对照；
已消费外部材料不重新消费。不把另一个模型投票当成客观裁判，当前 Agent 可以继续承担分析。

用户授权、证据来源、数据保留和已批准发布条件不由元反思自授予或解除。新需求也必须
显式声明兼容范围；不能把规则修改称作“优化”而悄悄改变 query_handoff 的字段含义。

## 10. 决策、停止与代码/数据恢复

| 观察 | 本轮决策 | 下一轮条件 |
|---|---|---|
| 检查/兼容失败，或实际数据/代码冲突 | 保留基线，已应用则按适用日志回退/前向修复 | 新证据或修订候选及剩余预算；保留原失败 |
| 已通过开发验收，但无真实结果或遥测不完整 | inconclusive，不能宣称长期改善 | 先补真实来源/缺失合同；不增加虚构评审 |
| 护栏满足，只有自然使用正向关联 | 在授权目标保持有限采用，并明确 observational 范围 | 新冻结窗口或有条件的独立对照 |
| 预声明对照支持目标效果且护栏满足 | 按证据与授权范围 adopt；不自动取得外部发布资格 | 新版本作为下一轮基线，继续监测旧能力 |
| 无新证据、轮次/成本用尽、用户停止、未知进程/冲突未解 | stop/保留未知，不自动续轮 | 用户新授权或实际外部状态改变；不靠换 ID 绕过 |

实际代码回退继续使用既有前后像，后续普通 Memory 写入保留。不能把数据库旧备份覆盖
当成回退；新数据模型要自己的兼容读写、备份、恢复/前向修复和升级后写入策略。
文件锁只协调合作写者，应用仍是逐文件原子替换；本方案不承诺整目录/活进程热更新。
