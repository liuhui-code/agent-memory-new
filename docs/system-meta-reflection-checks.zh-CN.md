# 系统元反思：显式检查计划与执行记录

日期：2026-10-30
状态：相关合成隔离回归已通过；不能据此认定完整功能通过，见[验证记录](system-meta-reflection-design.zh-CN.md#9-隔离验证记录)

## 本阶段目标

系统提案需要关联实际检查过程，不能把模型填写的 pass 或外部报告字符串当成
Runtime 亲自观察过的执行。本阶段增加显式检查入口，在授权开发副本中执行调用方
给出的有限计划，记录实际进程结果及检查前后的声明文件摘要。评审模型仍是用户
当前 Agent；普通查询、学习、反思存储和既有评测器不修改。

检查记录只证明观察到的进程事实。零退出码不认证测试有覆盖、预期合理、补丁已
应用或系统改善，因此不自动把提案推进为 checked，不解除现有发布和证据政策。
完整目标仍包括触发、提案、制品、真实检查、应用、观察及回退。

## 入口与计划

新增 `maintain-system-check`，继续通过 tools/agent_memory.py 调用。必需参数为
--id、--expected-revision、--run-key 和 --plan-file；默认仅预览，只有显式 --execute
才会预留执行记录并启动进程。检查命令可能产生自身副作用，调用方必须拥有对应
开发副本和命令授权；它不是隔离沙箱或只读命令分类器。

计划支持严格的 system-change-check-plan/v1、v2、v3 JSON，至多 32 KiB；共有字段为：

| 字段 | 含义 |
|---|---|
| schema_version | 固定格式标识 |
| proposal_id / prepared_state_revision | 精确绑定当前 prepared 提案及状态修订 |
| artifact_digest | 维护详情返回的制品身份摘要；覆盖根目录、声明基线和制品文件的路径、大小及原始字节摘要 |
| source_files | 1–100 个目录内的文件，每项仅含 path/digest；单文件至多 1 MiB，摘要为 SHA-256 |
| checks | 1–5 项，每项仅含 key、argv、assertion_indices、timeout_seconds |

v2 额外必需 candidate_key/candidate_digest，引用实际准备的独立候选；详见
[候选契约](system-meta-reflection-candidates.zh-CN.md)。v1 保持声明文件观察语义，
不事后获得补丁已应用或完整候选主体证明。

v3 保留候选绑定，并要求每个 check 声明 1–10 个 result_files；新运行开始前
这些路径不存在且不互为别名，执行后观察各至多 1 MiB 的产物摘要。缺少产物与
实际退出码分别保留；不能用旧产物支持新运行。专用 accept 入口只接受 v3
实际产物及预声明验收计划，见[生命周期规格](system-meta-reflection-lifecycle.zh-CN.md)。

计划文件本身须位于声明开发根目录内。v1 的 source_files/cwd 是该开发目录，
v2 则是已登记候选目录，自动追加全部补丁变更路径和 Git 状态观察。
argv 是 1–64 项字符串，每项至多 1,000
字符；首项为绝对可执行文件路径，不经 shell 解释。检查 key 为不透明标识；
assertion_indices 是提案 acceptance_criteria 的从 0 起下标，计划须声明覆盖全部
断言，但这种映射仍是调用方声明。每项超时 1–300 秒，总超时至多 600 秒。

只执行准备制品仍匹配、声明源码仍匹配且提案修订未改变的计划。每项检查前后
重新观察制品和声明源码；漂移时停止后续检查。仅进行有界文件观察，不能证明
整个仓库原子冻结、未声明文件不变或中途改动后恢复的情况。

## 记录、重试和隔离

首次显式执行才在既有归档创建可选 system_change_check_runs 表及其独立 schema
组件。预览和维护读取不建表。同一提案最多一项 running 记录；预留后立即提交，
不在整个进程执行期间持有 SQLite 写锁，后续状态写入保持与普通查询独立。

run-key 在项目内唯一。同内容终态重试只返回原历史，不重新核对今天的文件；内容不同拒绝，running 不
自动重试。硬崩溃留下的 running 表示结果未知，不按时间推断进程已终止，也不
自动重开检查。可控中断会先终止所持进程再记录 interrupted；不宣称可控制已经
脱离进程组的工作进程。

SQLite 只存计划摘要、检查身份和断言映射、超时、文件绑定、时间、实际退出码与
结果，不保存 argv、stdout、stderr、日志正文或私有推理。子进程标准输入和输出
连接 DEVNULL；需要诊断时由调用方在授权范围查看自己维护的检查产物。
这种设计防止把无界输出带入治理记录，不认证子进程自行产生的文件内容。
elapsed_ms 只计预留完成后的执行/观察阶段，截止最终写入前；不含最初读取、
预览、计划生成或最终提交，不能冒充用户端到端耗时。Token 未测量时保持 null。

执行使用无 shell 参数列表和有限等待；POSIX 使用独立进程组并在超时/中断时
终止所持进程组，其他平台至少终止直接子进程。参照
[Python subprocess 官方文档](https://docs.python.org/3.9/library/subprocess.html)。
本轮已在上述本机环境执行受控失败/超时等回归，其他平台和完整环境兼容性仍需检查。

维护详情返回有界历史执行摘要；指定运行键可读取一条完整、有界的执行记录。
运行结果与提案状态分别表达，记录明确包含 evidence_verified=false、
promotion_eligible=false 和 application_performed=false。
预览和全零退出的运行返回码为 0；命令失败、超时或执行中漂移返回码为 1，
但正文仍是执行记录，便于审查失败。输入/存储错误沿用治理错误结构。中断时
未观察到的进程事实保留未知，不能用旧的成功结果填补。

## 与完整生命周期的边界

本阶段不能代替真实使用触发保证、完整源码/环境绑定、独立断言审查、实际应用、
数据迁移、发布或回退执行。规则、Query、Learn、Reflect、结构等候选仍按各自
证据进入开发与检查，不能以增加治理记录代替实际改进。

新增用例位于 [test_system_evolution_checks.py](../tests/test_system_evolution_checks.py)。
验收方向为：预览无写入、漂移不执行、同键不重跑、真实退出失败不能填成功、
超时中止、状态并发受限、有限历史读取和普通查询隔离。对应合成回归已通过，
专用生命周期入口另行核对晋级、实际应用和回退条件；本检查入口独立不足以
证明这些后续动作或真实使用效果。额外业务项目部署另行绑定用户指定的目标。
