# ArkTS Real-Project Generalization Calibration

## Decision

Freeze the served retrieval policy while establishing a native ArkTS
generalization calibration loop. The local Runtime continues to supply compact,
auditable context; the Agent remains responsible for diagnosis and design.
No fifth Skill, daemon, vector database, or new diagnosis facade is introduced.

## Evidence

The development Context gate passes all 192 variants, while the release decision
denies promotion across 72 immutable real-project cases. The repeated failure
classes are candidate generation, ranking precision, and passage selection.
This is a distribution-generalization problem, not evidence that another broad
retrieval feature is needed.

## Evaluation Contract

New native ArkTS holdouts may declare `governance.calibration`. Each case must
then carry hidden `evaluation_profile` metadata:

- `target_domain`: `native_arkts`;
- `artifact_roles`: page, service, store, utility, component, adapter, or
  viewmodel;
- `target_levels`: file, callable, or expression;
- `mechanism_kinds`: bounded taxonomy of resource I/O, state, navigation,
  platform API, async control, persistence, event binding, or error contract.

Profiles are excluded from public Agent case payloads and compact Context. The
evaluator reports per-stratum metrics and macro averages only. A calibration
contract validates case count, required coverage, and `.ets` expected targets.
Historical sealed packs have no new fields and retain their original digests.

## Workflow

1. Use only aggregate failure distributions from consumed holdouts.
2. Create independent development cases without external repository names,
   paths, identifiers, task wording, expected files, or Oracle values.
3. Repair one repeatable failure class only after the independent development
   calibration gate identifies it.
4. Run focused tests, full development evaluation, scale gate, and full suite.
5. Create and source-review a new native ArkTS holdout, apply the calibration
   contract, seal it, and run Context once.
6. Run paired Agent A/B only if both Context and calibration gates pass.

## Method Basis

The separation of development and immutable evaluation follows TREC-style
retrieval evaluation, SWE-bench revision-grounded tasks, and BEIR-style
out-of-domain validation. The repository validation plan records the project
specific application and links to the primary references.

## Acceptance

- Calibration profile validation and aggregation are deterministic and
  evaluation-only.
- Historical seals verify unchanged.
- The independent ArkTS development pack covers service/file/resource I/O,
  page/callable/UI state, and utility/expression/navigation.
- A future native ArkTS holdout is eligible for Agent A/B only after its
  Context and calibration gates pass.

## Governed Repair: Callable Behavior Evidence

Two project-neutral reproductions isolated the retained failure classes without
using the frozen holdout's repository names, paths, identifiers, wording, or
Oracle values:

- a state-controlled page renderer was recalled at file level but its caller
  site outranked the conditional state branch;
- a lifecycle activation callable was recalled but an event-name lexical match
  outranked it.

The repair adds bounded, source-proven callable hints to existing method
evidence: lifecycle activation, deferred execution, instance-state read/write,
and conditional state branch. Query text maps only multi-term behavioral
descriptions to these normalized labels. Candidate recall receives a separate
bounded method-evidence lane, and compact focus gives complete structural
coverage precedence over a partial lexical match. The Runtime still returns
source anchors only; it does not infer an incident cause or repair.

The independent reproduction pack now passes 3/3 with exact top-1 anchors and
source spans. The pre-existing independent calibration pack also passes 3/3.
The HarmoneyOpenEye pack remains consumed and must not be rerun. The next
product-level evidence must be a newly sourced, sealed native ArkTS holdout.

## Second Repair: Guarded Recurring Work

The new project-neutral multi-layer reproduction pack initially isolated a
ranking-only error: the correct callable and exact source range were recalled,
but a status-only neighbor was also promoted as a primary anchor. The repair
adds the bounded `guarded_recurring_work` behavior concept. It requires a
multi-term description of repeated scheduled work and matches only existing
source-proven markers for deferred execution, an instance-state branch, and an
instance-state read. Thus a complete owner contract suppresses a partial
lexical neighbor without expanding the candidate set.

- Focused behavior tests pass.
- The multi-layer independent pack passes `3/3`, with exact anchor, precision,
  and source-span recall of `1.0`, at 628.7 estimated tokens per case.
- The complete 675-test suite and the 100,000-entity `eval-scale` CI gate pass.

This is development evidence only. It does not change the two consumed
holdout outcomes or authorize Agent A/B. A third, previously unused source
must be sealed and executed once before considering promotion.

## Evaluation Isolation Correction

A third source was audited and sealed, but its one Context invocation used a
configured memory home inside the source tree. Initialization created Runtime
artifacts before the source workspace was materialized, so the run is an
infrastructure-invalid observation rather than retrieval evidence. Its `0/3`
result is retained under an explicit invalid-result artifact for audit only;
it does not alter capability metrics and cannot be used for tuning or rerun.

The Context evaluator now rejects any explicit memory home that equals,
contains, or is contained by the source directory before initialization. The
canonical path check covers macOS `/var` and `/private/var` aliases. Native
ArkTS calibration now also has an explicit `viewmodel` artifact role rather
than coercing that layer into a service or adapter. The next valid external
gate must use a fourth, previously unused source and a sibling memory home.

## Fourth Native ArkTS Observation

The fourth source used a sibling memory home and passed the isolation guard,

selection before another independent source is considered.

## Third Repair: Guarded State Persistence

A fresh, project-neutral three-layer fixture family reproduced a ranking-only
failure after complete candidate and source-range recall: a summary interaction
shared state vocabulary with the correct state-transition callable. The repair
adds a source-proven persistence-write marker for receiver calls beginning with
`save`, `store`, `persist`, or `write`. A guarded selection query must contain
both state-transition and persistence language before this extra marker is
required, so a complete guarded-and-persisted owner outranks an incomplete
state-only neighbor.

The independent fixture family passes `3/3`, with anchor recall, precision,
and source-span recall all `1.0` at 615.3 estimated tokens per case. The full
test suite and line-limit gate pass. This is development evidence only: the
fourth source remains consumed at `0/3`, and a fifth unused source is required
for the next external Context gate.
