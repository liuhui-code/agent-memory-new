# 设计质量反思与元反思

在有实质设计取舍、实现偏差或维护反馈时选读。这里的“品味”指边界、抽象、总复杂度、
可演进性和有依据的取舍，不是命名偏好、短代码、模式数量或模型自评总分。
当前 Agent 做判断；Skill 组织问题，Runtime 沿用现有保存、隔离和治理合同。

## 第一层：这次设计实际怎样

先保留做决定时的目标、约束、可信变化和未知，再看实际产物与反馈。
区分已实施/检查的行为、对质量的意见、计划中的收益；设计讨论完成不证明实现或长期收益。
局部明确修改不需要强行补齐架构评审表，也不为每轮对话新增反思。

| 审查维度 | 决定性问题 | 可审阅依据与反例 |
|---|---|---|
| 边界 | 易变决定是否隐藏，状态与提交归谁，调用方必须知道什么？ | 当前调用/数据路径；把检查分散到每个调用方可能减少局部代码却增加整体负担 |
| 抽象 | 接口或层次是否解决真实变化，还是提前建立通用框架？ | 已存在的变体与调用者；函数、类、队列都可能合适，不按形式判优 |
| 总复杂度 | 复杂度被消除，还是转给调用方、配置、失败恢复或运维？ | 调用方接线、状态组合和失败路径；行数只作辅助信息 |
| 可演进性 | 一次有来源的变化实际传播到哪里，行为是否仍成立？ | 变化输入先后、实际补丁与验证；一个格式变化局部不证明任意未来变化局部 |
| 取舍 | 哪项质量优先、谁获得收益、谁承担代价，什么会推翻决定？ | 用户要求、适用契约与实际成本；缺少负载/Token 数据时保留 unknown |

实际引用案例时记录为何匹配、哪些前提未满足、借鉴/拒绝了什么。
成熟系统的名气、模板命中、测试通过和“感觉更优雅”都不单独认证设计质量。
用本项目已有事实反驳不合适的案例，而不是替案例补造需求。

### 通过已有普通 Reflect 字段保存

只保存值得复用的条件化教训，保留必需的 `task` 与 `lesson`，使用 `task_type: design`。
不新增 `taste_score`、`design_verified` 或另一套 Runtime schema。

| 已有字段 | 保存内容 |
|---|---|
| `context_used`, `source_cases` | 决定前后使用的源码、需求、案例与版本引用；外部参考不冒充本项目经历 |
| `reasoning_summary` | 简短决定理由、质量意见、重要备选与接受的代价；不存私有推理过程 |
| `hidden_assumptions`, `negative_preconditions` | 必需前提、未知及不能迁移的条件 |
| `what_worked`, `what_failed` | 实际观察和反证；标明开发反例、历史记录与真实事故的区别 |
| `verification_method`, `final_verification_path` | 实际执行或原有历史证据的引用；不要把计划写成已运行 |
| `future_rule`, `reuse_feedback` | 条件化建议、重审点、案例的有用/误导部分和收益未知 |

例如已有 P1 报告预览案例可记录“预先指定的 JSON 变化只改 renderer/测试”，
同时保留线程、顺序和实例范围的限制。这支持该变化下的局部性；“Memory 因此提高品味”仍未知。
故意错误原型是受控反例，不是旧 Agent 的实际基线。

重要决定留在 Git；普通反思只是经验候选。不要从一次成功设置 `procedure_experience`
或修改全局原则。误导复用可走已有 experience feedback，但普通设计反馈不自动启动系统元反思。

## 第二层：形成设计的方法哪里需要改

先读同目录的 [system-meta-review.md](system-meta-review.md) 和
[system-trigger.md](system-trigger.md)。本文件只增加审查内容，不改变触发、名额、预算或 schema。

### 何时触发

- 用户明确要求审阅 Memory 的设计支持，例如“复盘这次设计的边界与代价，并检查案例指导是否误导”。
- 否则仅在真实任务边界、已用或明确请求 Memory、并有既有合格信号时考虑自动评审：
  `memory_error`、`user_correction`、`evidence_conflict` 或 `repeated_gap`。
- 项目代码不够好、一次用例失败、普通设计反馈、没有命中案例，本身都不是 Memory 系统缺陷或新信号。
  要求开发本能力不等于授权一次真实手动评审；不能据此伪造 `manual_request`。
- 遵守用户停止、关闭和预算；系统评审/改进任务不递归自动评审。
  没有具体信号的成功任务仍不自动采样；不新增后台扫描或定时器。

### 找到影响决定的层

| 要审查什么 | 必须区别的原因 | 可能的既有目标组件 |
|---|---|---|
| 输入引导与原则 | 真正缺约束、Agent 未检查已有事实、指导本身误导，或需求后来变化 | `rules` / `reflect` |
| 查询与案例适配 | 需要的资料未返回、资料已返回但被误用、当前没有适配案例 | `query` / `rules` |
| 学习与经验复用 | 来源未记录、旧条件被遗漏、外部合同被写成项目事实 | `learn` / `memory` |
| 反思与评价 | 用“测试绿/文档长/模型赞同”替代质量证据，或遗漏代价与负例 | `reflect` / `evaluator` |
| 结构与版本表达 | 现有字段是否真的无法表达两类独立缺陷的共同必要信息 | `data_model` |

以上是定位问题，不是默认增加五个改动。失败层不明时记录缺口，不猜测检索权重或补新结构。
同一案例、一次反思的多次重放、多个相似意见不能充当独立证据。
跨任务审查仅使用已提供或已授权读取的任务、版本和反馈；没有真实来源就不制造长期趋势。

### 输出与后续改进

系统报告与普通项目反思分开。沿用 `system-meta-review/v1`：

- `observations` 保留可核对事实，`checks` 只给有预期依据与实际观察的断言标 pass/fail。
- 边界、抽象、复杂度、演进与取舍判断放在 `model_opinions`，包含依据和反证；
  没有依据时说明未知，不把“品味提高”设为检查通过。
- 在 `target_components` 指明涉及的现有层，至多给一个具体改进候选；
  有需要但证据不足用 `needs_evidence`，没有支持的问题则不给候选。
- 候选说明会改变哪条输入指导、案例前提、反思问题或已证明有缺陷的机制，以及代价、
  反例、验收与回退。改进也可能是删掉无效指导，不是持续堆案例或模板。

保持原上限：八个不同证据引用、检查与意见各至多五项、一个候选、4,000 字符及更小的用户预算。
不是要求每次写满五项；只检查影响此次决定的维度。沿用当前模型，不另接评审模型。
报告仅在已有授权与支持下通过 `reflect-system` 保存，不送入普通 `reflect` / `update`。
未测量的增量 Token/耗时保持 null，模型一致意见不等于独立验证。

之后经 Maintain 的既有候选/隔离检查/应用/回退流程推进；本审查不直接改规则、评分或数据库。
修改服务行为仍需独立开发复现和正式公共输出；改评价器需已知预期被误判；
改架构仍需至少两类独立缺陷指向同一缺失契约。不能因“品味”绕过这些门槛。

已有 R2/R3 轮次明确绑定设计指导效果时，可在既有授权窗口内使用相同问题审查后续反馈。
仍用原 R2 `summary` / `evidence_refs` 等字段，不向 R2 注入另一套报告，不自动创建轮次或续跑。
跨版本/长期效能需要真实任务来源和适用比较合同；旧 diagnosis cohort 不能改名复用。
