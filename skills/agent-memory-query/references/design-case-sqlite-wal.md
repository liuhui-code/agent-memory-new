# SQLite WAL：读快照的寿命也是设计约束

案例 ID：`sqlite-wal-snapshot`。类型：官方存储机制文档。
查阅于 2026-11-18；具体版本、构建和文件系统条件须在应用时核对。

## 来源事实

WAL 允许读取与写入并行，但同时仍只有一个写者。读事务保持自己的提交边界；
长读事务可能阻止 checkpoint 完成。常规 WAL 共享内存机制还要求访问进程位于同一主机。
见 [SQLite：Write-Ahead Logging](https://sqlite.org/wal.html)，
重点为 Concurrency、Avoiding Excessively Large WAL Files 及版本相关说明。

## 可借鉴的判断与代价

以下为迁移分析：一致性要绑定具体事务和生命周期，不能只给对象加一个“snapshot”名称。
长时间保持快照与及时回收写入历史存在取舍；缩短事务也可能改变用户看到的数据一致性。
复制到内存的选中条目不是数据库事务，多次分页请求也不会自然共享同一读视图。

## 匹配与失配

- 匹配：浏览、报告或导出与数据库写操作并行，需要明确读视图寿命。
- 未知：实际 journal mode、连接/事务寿命、写入压力及 checkpoint 条件。
- 反例：需要多主机共享文件或多个写者并行时，不能只凭 WAL 解决；也不因卡片建议自动切换配置。

## 本项目迁移假设

人工记忆审查中的“一页”“选中记录”“全库导出”应分别定义一致性要求。
本案例不声明当前 Runtime 已启用某模式，也不改变 SQLite 真相源。
若未来作此设计，检查并发更新时实际可见内容及长读的资源影响，而非只测试查询成功返回。
