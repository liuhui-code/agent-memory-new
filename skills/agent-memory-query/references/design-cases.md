# 有来源的成熟系统设计案例

这些卡片预置在 Skill 中，供 Agent 按问题特征选读。它们是外部参考，
不是本项目经验、已批准规范、验证通过的 procedure 或效能评测。
原文查阅于 2026-11-18，收录于 2026-11-19；原文可能更新，卡片不固定上游版本或证明当前部署状态。

## 按问题选择

| 问题特征 / 检索词 | 案例 | 值得核对的设计选择 | 最容易套错的前提 |
|---|---|---|---|
| 模块耦合、改动扩散、公开接口；boundary / coupling | [Shopify 模块化单体](design-case-shopify-modularity.md) | 责任和依赖边界与部署单元分别决定 | 需要独立发布、伸缩或强故障隔离时，单体未必合适 |
| 宿主与扩展、能力位置、按需加载；host / capability / activation | [VS Code Extension Host](design-case-vscode-host.md) | 按能力与运行位置划界，延迟激活 | 一个宿主不等于每个扩展都有安全沙箱 |
| 长读事务、读写并行、一致视图；snapshot / writer / checkpoint | [SQLite WAL](design-case-sqlite-wal.md) | 读快照、写入与 checkpoint 的生命周期 | WAL 不提供多写者并行，也不使跨请求分页自动成为同一快照 |
| 超时结果未知、重复提交；idempotency / retry / identity | [Stripe API v1 幂等请求](design-case-stripe-idempotency.md) | 操作身份、参数绑定与已执行结果的保存 | API 版本、键寿命和执行边界改变时不能照抄 |
| 请求成本不同、排队与拒绝；resource / overload / admission | [Google SRE 资源与准入](design-case-sre-overload.md) | 按真实资源成本限制工作，考虑上游节流 | 固定请求数不等于容量；拒绝本身也有成本 |
| 动态规则、模拟运行、批量发布；regex / simulate / rollout | [Cloudflare 2019 WAF 事故](design-case-cloudflare-waf.md) | 行为正确之外还要检查资源成本与影响范围 | “不阻断用户请求”不等于执行没有副作用 |

## 怎样使用

先确定当前易变决定、状态/数据所有者、寿命、失败和资源约束，再选相关卡片。
局部明确修改可直接完成；没有合适案例也是有效结果。不要默认加载六张卡片。
这张表是 Agent 的阅读索引，不是 Runtime 分类器、排名或自动模式选择。

案例影响决定时，留下简短说明：

- 哪个当前事实使它匹配；关键前提已确认、未知还是被否定？
- 借鉴哪条机制，接受什么代价；哪些原系统条件不迁移？
- 当前方案、另一种可行机制或直接实现相比，调用方和维护者承担什么？
- 用什么当前行为或可信变化检查选择；什么条件会使决定失效？

区别卡片中的“来源事实”和“迁移判断”。文档合同不等于真实事故证据，
团队报告的收益不等于独立测量；历史修复计划不等于后来已完成。
版本、配置或 API 行为影响决定时重新核对官方原文；可用时优先使用 Context7，
不可用时查官方来源。不要用卡片替代当前源码、约束和用户需求。

## 在本项目中的实际使用

本次“预置案例”需求适合借鉴 Shopify 的职责边界和 VS Code 的按需激活思想：
案例随既有 Skill 安装，主入口只指向索引，Agent 需要时才读卡片。
这里借鉴的是资料组织与加载边界，不复制部署形态、扩展宿主进程或团队工具。

另一种可行选择是独立的外部参考 Provider，以便由 Runtime 统一召回；它需要明确的来源等级、
检索与兼容合同。本次选择已有 Skill 资源，代价是 Agent 需要按索引择读，卡片也需要维护；
先满足预置可读材料的要求，不把它称为已经实现统一检索或自动适配。

没有把外部案例写成 SQLite 的项目事实或成功经历，也没有扩充 Runtime 的模式匹配。
`design-context` 仍走原协议；这些卡片不会自动出现在其静态设计目录里。
实际应用产生结果后，可经既有 Reflect 保存带来源、前提和反例的本项目经验候选。
若以后比较本指导包的收益，需要固定本次新版本，不能继续称它与旧 P2 的 23 资源基线相同。
