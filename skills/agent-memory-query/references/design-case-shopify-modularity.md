# Shopify：把职责边界与部署边界分开

案例 ID：`shopify-modular-monolith`。类型：团队作者的历史架构报告。
原文发布于 2019-02-21；查阅于 2026-11-18。不描述 Shopify 当前全部架构。

## 来源事实

作者报告业务域耦合使局部修改牵连其他功能，开发者需要理解过多上下文。
团队保留单个应用部署，按业务域建立组件、公开接口与数据归属；作者称依赖隔离帮助了
税务引擎替换。这是团队自述，不是独立对照结果。
见 [Shopify 原文：Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity)，
重点为 Modular Monoliths、Isolating Dependencies 和 Enforcing Boundaries。

## 可借鉴的判断与代价

以下为迁移分析：把一起变化的责任封在同一接口后，先减少调用方必须了解的细节，
再决定是否拆部署。仅移动目录而继续绕过接口，不解决原来的耦合。
保留一个部署单元可以降低分布式协作成本，但共享部署与运行资源的限制仍在，边界也需要维护。

## 匹配与失配

- 匹配：已有跨职责调用或改动扩散证据，同时希望保留简单部署和本地调用。
- 未知：哪些责任真正一起变化，谁拥有数据，调用者需要哪些稳定能力。
- 反例：已证实需要独立伸缩、独立发布或强故障隔离时，不能凭此排除服务拆分。

## 本项目迁移假设

若检索、源码适配与治理相互泄漏内部状态，可先审查现有模块接口和数据归属，
保留唯一 Runtime 入口。不能因为模块数量多就推断架构有问题，也不照搬 Rails/Wedge 工具。
检验一次真实改动是否能留在所属责任内、调用方是否少了解实现细节；文件数或边界评分不能单独判优。
